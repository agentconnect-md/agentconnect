# Connect AgentConnect to a self-hosted Gitea

AgentConnect talks to **one** Gitea instance per deployment: either gitea.com or
one instance you host, never both. Everything else about the integration —
identity, credentials, webhooks, reviews, commit statuses — is the same on
either.

This guide uses the RFC 2606 documentation name `https://gitea.example.test` and
the example repository `example-org/example-repo`. Replace both with your own.

Forgejo and Codeberg are **not** supported. Forgejo forked from Gitea 1.22 and
differs in the parts this integration depends on — token scopes, inline review
comments, webhook headers, the event vocabulary — and its version string parses
below the floor, so AgentConnect refuses it rather than half-working.

## What the instance must provide

| Requirement             | Why                                                                                                                                                                                                                  |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Gitea **1.23 or later** | The release where the scoped-token model and the review-request webhook are both stable. `GET /api/v1/version` answers without a token, so the floor is checked when the URL is saved and again at every connection. |
| **HTTPS**, one address  | Clone URLs, the repository addresses agents are given, and Gitea's own `html_url` values only agree if there is a single address. Split internal and external addressing belongs in DNS.                             |
| A trusted certificate   | There is no skip-verify option at any layer. A private authority is supported by installing its bundle — see below.                                                                                                  |
| **HTTP Git enabled**    | Clone, fetch, and push all run over HTTPS with the bot's token. SSH remotes and plain HTTP are outside the contract.                                                                                                 |

A path prefix (`https://gitea.example.test/gitea`) and a non-default port are
both supported and preserved everywhere.

An instance that drops below the floor after repositories are already set up
keeps serving them: existing sessions and credentials work, and only new setup
and token replacement are refused. AgentConnect records the version it observes
and the console shows it on the Gitea connection.

## Save the instance URL in Setup

Setup's Gitea card takes **one** value, the instance base URL. There is no
application to register and no client pair to enter: Gitea's OAuth provider would
add no identity of its own — an operation made with an OAuth token is attributed
to the authorizing user, exactly as with a token that user generated by hand — so
AgentConnect uses a bot user's token directly.

When the URL is saved, Setup probes the instance and applies the version floor.
Only an invalid URL or a version below the floor blocks the save; an unreachable
host, an untrusted certificate chain, or a response that is not a Gitea API root
are reported as warnings, because Setup and the rest of the deployment need not
share a network position.

**The base URL cannot be changed while Gitea state exists.** The stored token,
numeric repository IDs, webhook IDs, and cleanup obligations carry no instance
provenance, so retargeting would send one instance's credentials to another.
Remove every Gitea repository and disconnect the bot first.

## Create the bot user

One bot user serves the whole organization: every comment, review, commit status,
and commit an agent writes is attributed to it, and its token is the only Gitea
credential AgentConnect holds.

1. Create a **dedicated user** on your instance — not a person's account, and not
   an instance administrator. An administrator reads back as the owner of every
   repository, which would make the permission checks meaningless.
2. Sign in as that user and open **Settings → Applications → Manage Access
   Tokens**.
3. Generate a token with exactly these four scopes:

   | Scope               | What it is for                                                       |
   | ------------------- | -------------------------------------------------------------------- |
   | `read:user`         | Reading the bot's own identity, and the organizations it belongs to. |
   | `write:repository`  | Webhook management, commit statuses, reviews, and repository reads.  |
   | `write:issue`       | Comments and reactions on issues and pull requests.                  |
   | `read:organization` | Listing an organization's repositories for the console's picker.     |

   Gitea shows the token once. It carries **no expiry** — Gitea does not issue
   expiring tokens, and cannot create or revoke one without the user's password —
   so there is no rotation AgentConnect can drive. Replacement is a console
   action, and revoking the old token is a step you take in Gitea.

4. Paste the token into **Integrations → Code hosts → Gitea → Connect Gitea** in
   the console. AgentConnect verifies the bot's identity, the version floor, and
   each of the four scopes before it stores anything, and it refuses a token whose
   user already serves another organization on this deployment.

The token is sealed at rest, never returned by any API, and reaches a daemon only
as a short lease over its authenticated connection. It is broad by construction:
an agent working in a bound repository can do anything the bot can there,
including changing that repository's settings. Scope it by choosing which
repositories the bot may administer, not by splitting the token.

## Give the bot Admin on each repository

AgentConnect installs, repairs, tests, and removes each repository's webhook
itself, and Gitea's webhook routes require repository **administration**. So for
every repository you want agents to work in, add the bot as a collaborator with
**Admin**, or put it in a team that has Admin:

- Per repository: **Settings → Collaborators → Add collaborator**, permission
  **Administrator**.
- Per organization: a team with the **Administrator** unit access, then add the
  bot to it.

The console's repository picker lists only repositories where the bot holds Admin
right now, so a repository that does not appear is a permission to grant rather
than a bug. A bot demoted to Write later keeps serving sessions — comments,
reviews, commit statuses and Git all need only Write — but the repository enters
**setup incomplete**, webhook repair is suspended, and membership checks fail
closed, because the permission lookup AgentConnect authorizes contributors with
also needs Admin.

## Let Gitea reach the webhook endpoint

Gitea refuses webhook deliveries to loopback and private addresses by default.
The refusal happens at **delivery** time, not at creation: the webhook installs
cleanly and then stays silent.

If your AgentConnect ingress endpoint resolves to a private address, add its host
to `ALLOWED_HOST_LIST` under `[webhook]` in `app.ini`:

```ini
[webhook]
ALLOWED_HOST_LIST = agentconnect.example.test
```

The value accepts host names, CIDR ranges, and the built-in groups (`private`,
`loopback`, `external`, `*`); prefer naming the one host over opening a whole
group. Restart Gitea after editing `app.ini`.

AgentConnect fires a test delivery as the last step of adding a repository and
waits for it to arrive. One that never does leaves the repository **ready** with
a warning naming this setting, so a blocked address is visible at setup time
rather than after the first missed pull request. Fix the allowlist, then press
**Repair** on the repository row — or simply wait for the first real delivery,
which clears the warning too.

## Certificate authority bundle

If your instance presents a certificate from a private authority, the bundle must
be readable **at a file path that exists inside each process**, including the
agent sandbox. Point every runtime at it:

| Variable              | Reached by                                         |
| --------------------- | -------------------------------------------------- |
| `NODE_EXTRA_CA_CERTS` | The orchestration service and the daemon (Node.js) |
| `SSL_CERT_FILE`       | Tools that read the OpenSSL default bundle         |
| `SSL_CERT_DIR`        | The hashed-directory form of the same              |
| `GIT_SSL_CAINFO`      | Git itself, for clone, fetch, and push             |

A path that exists only on the host is not enough: an agent runs in a sandbox with
its own filesystem view, so the bundle has to be mounted there too, and the
variables have to survive into the sandbox environment. Set them where the sandbox
image and its environment are configured, not only on the host.

## Network access

Three components need to reach the instance, and one does not:

- **The orchestration service** calls the Gitea API outbound over HTTPS for every
  administrative action: version checks, repository reads, webhook management and
  test deliveries, membership lookups, and commit statuses.
- **The daemon** calls the API for turn-time reads and effects, and clones,
  fetches, and pushes over HTTPS.
- **The agent sandbox** clones and pushes over HTTPS. There is no Gitea CLI
  wrapper: an agent reads and writes through the provider tools.
- **The public ingress endpoint that terminates Gitea webhooks never dials
  Gitea.** It only receives. It needs no certificate bundle and no outbound access
  to the instance.

Traffic runs to the one base URL you configured. Mutual TLS and an outbound HTTP
proxy are not supported.

## Allow the daemon to clone your instance

Nothing to do for the instance you configured: a daemon authorizes a clone against
the code host the agent's own specification names — the same address it already
uses to decide where that agent's Git credential may go — so a workspace on your
instance, or an additional repository on it, clones with no local configuration
anywhere.

The operator policy behind that is `security.workspaceGitAllowedOrigins` in a
daemon's config file (`daemonPool.workspaceGitAllowedOrigins` in the Helm chart,
where members have no config file). Reach for it only to allow something _else_ —
a second host, an SSH remote — or to restrict: an explicit empty list turns remote
Git workspaces off entirely, and nothing is adopted past that.

## Checklist

1. Instance is 1.23 or later, on HTTPS, at one address, with HTTP Git enabled.
2. Instance base URL saved in Setup; probe warnings understood.
3. Dedicated bot user created, and a token generated with `read:user`,
   `write:repository`, `write:issue`, and `read:organization`.
4. Bot given **Admin** on every repository agents will work in.
5. `ALLOWED_HOST_LIST` under `[webhook]` names the ingress host if it is on a
   private network.
6. Private authority bundle mounted and exported to the orchestration service,
   the daemon, and the sandbox.
7. Connect the bot in the console, add a repository, and confirm it reaches
   **ready** with no webhook warning.
